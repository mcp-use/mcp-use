MCP Events let a client subscribe to updates from your server, such as a new
message in a channel, and receive each one as a signed webhook. mcp-use
implements the dialect ChatGPT uses
([OpenAI MCP Events](https://developers.openai.com/plugins/build/mcp-events)):
webhook delivery only, with callback verification and Standard Webhooks
signatures.

## Define and emit an event

```ts
import { MCPServer } from "mcp-use";
import { z } from "zod";

const server = new MCPServer({ name: "chat", version: "1.0.0" });

const messageCreated = server.event({
  name: "message.created",
  description: "A message was posted in a channel you follow.",
  inputSchema: z.object({ channel_id: z.string() }),
  payloadSchema: z.object({
    channel_id: z.string(),
    message_id: z.string(),
    preview: z.string(),
  }),
});

// Later, when a message is posted:
await messageCreated.emit(
  { channel_id: "c1", message_id: "m42", preview: "Hi" },
  { eventId: "m42" },
);
```

- A subscription matches when every argument that has a same-named top-level
  field in `data` is equal (`channel_id` above). Pass `matches(args, data)` to
  filter differently.
- `eventId` should be stable for the underlying change: it is sent as
  `eventId` and as the `webhook-id` header, and receivers deduplicate on it.
  It is generated when omitted.
- `emit` validates `data` against `payloadSchema`, rejects bodies over 256 KiB,
  and resolves after the first delivery attempt to each matching subscription.
- `emit` throws if the store is unreachable. When the event follows a write
  that already succeeded, catch the error and log it so the tool call does not
  fail:

  ```ts
  await noteCreated
    .emit({ folder, noteId, title }, { eventId: noteId })
    .catch((err) => console.error(`note.created emit failed: ${err}`));
  ```

## What the server does

Registering an event advertises `capabilities.events: {}` on `initialize` (and
`server/discover`) and serves:

| Method               | Behaviour                                                                                                                                                                         |
| -------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `events/list`        | Event names, descriptions, `delivery: ["webhook"]`, `inputSchema`, `payloadSchema`.                                                                                               |
| `events/subscribe`   | Validates the name, arguments and `whsec_` secret (24-64 bytes), verifies the callback, stores the subscription. Returns `{ id, refreshBefore, cursor: null, truncated: false }`. |
| `events/unsubscribe` | Removes the subscription matched by name, arguments and callback URL. Idempotent; returns `{}`.                                                                                   |

mcp-use answers `events/*` before the MCP SDK handler, so a future SDK version
with its own Events handlers cannot take these methods over.

**Subscription identity.** The id is derived from the authenticated principal,
callback URL, event name and arguments. Subscribing again with the same values
refreshes it. `ttlMs` omitted grants 24 hours (configurable with
`events.defaultTtlMs`), a number is clamped to 1 minute - 30 days, and `null`
means no expiry (`refreshBefore: null`).

**Callback verification.** Before the first subscription for a principal and
URL, the server POSTs a signed `{"type":"verification","challenge":"..."}` and
expects a 2xx response echoing `{"challenge": "..."}`. Success is cached for an
hour. Failure returns JSON-RPC error `-32015` with `data.reason`
(`challenge_failed` or `timeout`).

**Delivery.** One event per POST with body
`{ eventId, name, timestamp, data, cursor: null }` and headers `webhook-id`,
`webhook-timestamp`, `webhook-signature` (`v1,<base64 HMAC-SHA256>`) and
`X-MCP-Subscription-Id`. Failures are retried after 10 s, 1 min, 5 min, 30 min
and 2 h with the same `eventId`; `410` (which also removes the subscription)
and `413` are not retried. When a subscribe call brings a new secret, deliveries
are signed with both secrets for 24 hours.

**Callback safety.** Callbacks must be HTTPS. On Node, the sender resolves the
host, rejects private, loopback and link-local addresses, and connects to the
validated address (no DNS rebinding); redirects are not followed and each
request times out after 10 s.

## Storage

| Where          | Store                                                                                                                |
| -------------- | -------------------------------------------------------------------------------------------------------------------- |
| `mcp-use dev`  | Memory (resets on restart). `http:` and loopback callbacks are allowed.                                              |
| Manufact Cloud | Redis through the platform proxy, from `MCP_USE_PLATFORM_STORAGE_URL`, `_TOKEN` and `_PREFIX`. Nothing to configure. |
| Self-hosted    | Any Upstash REST endpoint:                                                                                           |

```ts
import { upstashEventsStore } from "mcp-use/events";

new MCPServer({
  name: "chat",
  version: "1.0.0",
  events: {
    store: upstashEventsStore({
      url: process.env.UPSTASH_REDIS_REST_URL!,
      token: process.env.UPSTASH_REDIS_REST_TOKEN!,
    }),
  },
});
```

Other platform variables: `MCP_USE_PLATFORM_NAMESPACE` (key namespace) and
`MCP_USE_PLATFORM_SECRET` (encrypts stored webhook secrets; comma-separated for
rotation). At startup the server logs which store is active (in-memory, custom,
or Upstash REST with the host only, never the token).

### Tick and health routes

Both routes live under the MCP path (`basePath`, `/mcp` by default), not the
server root:

- `GET|POST /mcp/_mcp-use/events/tick` runs due delivery retries. Call it from
  a cron on serverless hosts, where no background timer survives.
- `GET /mcp/_mcp-use/events/health` reports the Events runtime status.

Both require `Authorization: Bearer <secret>`, where the secret is a value of
`MCP_USE_PLATFORM_ADMIN_SECRET` or `CRON_SECRET` (each may be a comma-separated
list). When neither variable is set, the routes are disabled.

```bash
curl -X POST https://example.com/mcp/_mcp-use/events/tick \
  -H "Authorization: Bearer $CRON_SECRET"
```

### Delivery history and admin routes

Every webhook attempt (verification challenges, event deliveries, retries and
final failures) is logged as one line,
`[mcp-use] events delivery <name> <subscriptionId> -> <origin> <status|error> <ms>ms attempt <n>`,
and recorded in the events store for 7 days (at most 1000 records). A record
holds `id`, `kind` (`verification` or `event`), `eventId`, `name`,
`subscriptionId`, `callbackOrigin` (scheme, host and port only), `attempt`,
`status` (`null` on a network error), `ok`, `error`, `durationMs` and `at`.
Recording never fails a delivery.

Two read-only routes expose this. They accept only
`MCP_USE_PLATFORM_ADMIN_SECRET` (not `CRON_SECRET`) and return 404 when it is
unset:

- `GET /mcp/_mcp-use/events/admin/subscriptions` returns
  `{ subscriptions: [{ id, name, arguments, callbackOrigin, clientName, createdAt, refreshBefore, expiresAt, lastDelivery }] }`.
  `lastDelivery` is `{ at, ok, status }` or `null`.
- `GET /mcp/_mcp-use/events/admin/deliveries?subscriptionId=&limit=` returns
  `{ deliveries: [...] }`, newest first (`limit` 1-200, default 50).

Neither route returns webhook secrets or full callback URLs.

## Receive events in a client

```ts
import {
  createWebhookReceiver,
  generateWebhookSecret,
  subscribeEvent,
  unsubscribeEvent,
} from "@mcp-use/client";

const secret = generateWebhookSecret();
const handler = createWebhookReceiver({
  secrets: [secret],
  onEvent: (event) => console.log(event.name, event.data),
});
// Serve `handler` (a Fetch handler) at https://example.com/hooks/mcp

await subscribeEvent(session, {
  name: "message.created",
  arguments: { channel_id: "c1" },
  url: "https://example.com/hooks/mcp",
  secret,
});
```

The receiver checks the signature and timestamp, answers the verification
challenge and ignores repeated `eventId`s. Call `subscribeEvent` again before
`refreshBefore` to keep the subscription; `unsubscribeEvent` stops delivery.

## Inspector

The Inspector's **Events** tab lists the server's events and subscribes with
the Inspector's built-in webhook inbox as the callback. Each delivery shows its
`webhook-id`, signature check and body. Under `mcp-use dev --tunnel` the inbox
callback path is the only Inspector path reachable through the tunnel.

See `examples/mcp-events` for a complete server.
